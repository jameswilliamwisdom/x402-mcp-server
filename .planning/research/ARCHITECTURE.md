### Structure Rationale

- **`site/` as subdirectory:** Keeps brand site in the same repo as the code it documents. No monorepo tooling (Turborepo, nx) needed at this scale — `site/` just has its own `package.json` and you `cd site && npm run build` independently.
- **`site/` is NOT published to npm:** The `files` field in the root `package.json` explicitly includes only `dist/` and `README.md`. Astro site never enters the npm bundle.
- **`openapi/` stays at root:** The Astro docs pages can reference or inline spec content. Not duplicating it into `site/`.
- **`site/dist/` gitignored:** Static build output is deployed via rsync/scp — no need to version it.
- **Separate `site/package.json`:** Astro and its deps don't bloat the published npm package. Consumers of `x402-mcp-server` never download Astro.

## Architectural Patterns

### Pattern 1: Explicit npm `files` Whitelist

**What:** Use `files` array in `package.json` to whitelist exactly what ships to npm. Default (no `files`) includes everything, which would publish `.planning/`, `site/`, `openapi/`, and source maps.

**When to use:** Always for MCP server packages — the installable artifact is just `dist/` plus `README.md`.

**Trade-offs:** Slightly more maintenance if new top-level dirs are added; prevents accidental secret/planning file leaks.

**Example:**
```json
{
  "files": ["dist", "README.md"],
  "engines": { "node": ">=18" },
  "scripts": {
    "prepublishOnly": "npm run build"
  }
}
```

### Pattern 2: `bin` Entry with Shebang

**What:** The existing `bin.x402-mcp-server` points to `dist/index.js`. Claude Desktop and other MCP clients invoke this directly. The shebang `#!/usr/bin/env node` is already in `src/index.ts` and will be in `dist/index.js` after compile.

**When to use:** Required for any MCP server distributed via npm — MCP clients need a CLI entry point.

**Trade-offs:** None. Required pattern. Ensure `dist/index.js` has execute permissions (`chmod +x`) — `npm publish` preserves file mode.

**Example (MCP client config after npm publish):**
```json
{
  "mcpServers": {
    "x402": {
      "command": "npx",
      "args": ["-y", "x402-mcp-server"],
      "env": { "X402_PRIVATE_KEY": "0x..." }
    }
  }
}
```

### Pattern 3: Astro Static Output for Self-Hosting

**What:** Astro's default `output: 'static'` mode produces a `site/dist/` directory of pure HTML/CSS/JS that can be served by any static file server.

**When to use:** Any docs/marketing site that doesn't need server-side rendering or dynamic routes. Matches the self-hosting constraint exactly.

**Trade-offs:** No server-side search (use Pagefind for static search), no dynamic data (pricing/API status must be hardcoded or fetched client-side). For this project that's fine — pricing is static, status is checked live by the MCP tool.

**Example `astro.config.mjs`:**
```javascript
import { defineConfig } from 'astro/config';

export default defineConfig({
  output: 'static',
  site: 'https://x402.network',  // or whatever domain
});
```

## Data Flow

### npm Package Flow

```
Developer runs: npm install x402-mcp-server
                        │
              npm registry (dist/ + README.md only)
                        │
              Agent MCP config: "command": "npx -y x402-mcp-server"
                        │
              dist/index.js spawned as subprocess
                        │
              StdioServerTransport ←→ MCP client (Claude Desktop, etc.)
                        │
              Tool call → x402-fetch → Railway API (402 → payment → result)
```

### Brand Site Build + Deploy Flow

```
cd site && npm run build
        │
   Astro compiles src/pages/ + src/content/ → site/dist/ (static HTML/CSS/JS)
        │
   rsync site/dist/ user@homeserver:/var/www/x402-network/
        │
   nginx serves site/dist/ at x402.network (or local domain)
```

### Key Data Flows

1. **npm publish:** `npm run build` (tsc) → `dist/` → `npm publish` ships only `files: ["dist", "README.md"]` to registry. The `prepublishOnly` script guarantees build runs before publish.
2. **Docs site ↔ source of truth:** Astro pages reference API pricing and tool descriptions. These are currently hardcoded in both `src/index.ts` and the future docs pages — no runtime coupling. If pricing changes, both need manual updates (acceptable at this scale).
3. **MCP tool invocation:** Unchanged from existing. npm publish doesn't change the runtime behavior — it just makes the existing `dist/index.js` installable without cloning the repo.

## Scaling Considerations

| Scale | Architecture Adjustments |
|-------|--------------------------|
| Current (1 dev, personal use) | Monorepo with manual deploy — correct approach |
| Public launch (dozens of agent installs) | No changes needed — npm handles distribution, static site handles docs |
| High-traffic docs (10k+ monthly visits) | Add CDN in front of self-hosted nginx; still static so trivially cacheable |
| Many new tools/APIs | Split `src/index.ts` into `src/tools/` modules; Astro content collections handle more docs pages automatically |

### Scaling Priorities

1. **First bottleneck:** `src/index.ts` monolith becomes hard to navigate at 10+ tools. Fix: extract each tool group to `src/tools/screenshot.ts`, `src/tools/pdf.ts`, etc., imported by a thin `src/index.ts`. Zero impact on npm package or site.
2. **Second bottleneck:** Docs site pricing/tool info drifts from actual MCP server. Fix: generate docs content from TypeScript constants shared between `src/index.ts` and site build. Not needed yet.

## Anti-Patterns

### Anti-Pattern 1: Publishing Without `files` Whitelist

**What people do:** Run `npm publish` without setting `files` in `package.json`.

**Why it's wrong:** Ships `.planning/`, `openapi/`, `site/`, `node_modules/` (if not gitignored), and potentially `.env` to the public registry. Can't un-publish — npm retains package contents.

**Do this instead:** Add `"files": ["dist", "README.md"]` before the first publish. Verify with `npm pack --dry-run`.

### Anti-Pattern 2: Astro Site in a Separate Repository

**What people do:** Create `x402-network-site` as its own repo to keep it "clean".

**Why it's wrong:** API documentation must stay synchronized with the MCP server's tool definitions and pricing. A separate repo creates a documentation drift problem and doubles the PR/deploy overhead for what is a single product.

**Do this instead:** `site/` subdirectory in the same repo. One commit can update both the tool definition and its documentation page. The Astro site is isolated from npm via the `files` whitelist.

### Anti-Pattern 3: Using `npx` Without `-y` in MCP Config

**What people do:** Configure MCP clients with `"command": "npx"` and `"args": ["x402-mcp-server"]`.

**Why it's wrong:** npx may prompt "Install x402-mcp-server? (y)" — interactive prompts break MCP stdio transport, which expects JSON on stdin immediately.

**Do this instead:** Always use `npx -y x402-mcp-server` in MCP client configs. Document this in README and brand site.

### Anti-Pattern 4: Astro SSR Mode for a Static Docs Site

**What people do:** Use `output: 'server'` or `output: 'hybrid'` for docs/marketing pages.

**Why it's wrong:** Requires a Node.js server process running on the home server, adds operational overhead, and gains nothing for content that doesn't change per-request.

**Do this instead:** `output: 'static'` (Astro default). Serves from nginx as static files with no runtime process.

## Integration Points

### External Services

| Service | Integration Pattern | Notes |
|---------|---------------------|-------|
| npm registry | `npm publish` from repo root | Gated by `files` whitelist; `prepublishOnly` runs build |
| Home server | `rsync site/dist/` via SSH | nginx serves static output; no server process needed |
| Railway APIs | Unchanged — HTTP via x402-fetch | No changes to runtime behavior from npm publish |
| MCP clients (Claude Desktop, etc.) | `npx -y x402-mcp-server` CLI invocation | bin entry in package.json already configured |

### Internal Boundaries

| Boundary | Communication | Notes |
|----------|---------------|-------|
| `src/index.ts` ↔ `site/` | None at runtime — docs are static | Pricing/tool names are duplicated; accept this at current scale |
| `package.json` ↔ npm publish | `files` field controls bundle | `prepublishOnly` enforces fresh build |
| `site/` ↔ `openapi/x402-network.yaml` | Optional build-time read | Astro can `import` YAML during build to auto-generate endpoint tables; treat as nice-to-have |
| Root `tsconfig.json` ↔ `site/tsconfig.json` | Separate — Astro manages its own TS config | Do not merge; Astro's TS config has different targets and includes |

## Build Order

The following order respects dependencies between the two new components:

1. **Harden `package.json` for npm publish** — add `files`, `engines`, `prepublishOnly`. This is prerequisite to publishing and has zero risk.
2. **Add `.gitignore` entries** — `site/dist/` before creating the site directory.
3. **Update README.md** — add `npx -y x402-mcp-server` install instructions and config examples. Can be done before or after npm publish.
4. **First npm publish** — establishes the package on the registry. Brand site can reference it by name in install instructions.
5. **Scaffold Astro site in `site/`** — `npm create astro@latest site` or manual scaffold. Does not block npm publish.
6. **Build Astro content** — pages, docs, pricing, getting started guide.
7. **Deploy brand site** — rsync to home server.

Steps 4 and 5 are independent. npm publish can happen while the brand site is being built.
